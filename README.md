# Delhivery Last-Mile Delay Intelligence Pipeline

Capstone project — AI & ML Certification Program, E&ICT Academy, IIT Roorkee.

One connected pipeline that answers three operations questions for a regional Delhivery team, on **synthetic** data produced by `generate_data.py`:

1. **How long will a parcel take?** — a delivery-hours regression (Part B).
2. **Which parcels will miss their promise?** — a delay classifier with an alert threshold chosen for the operations rule (Part C).
3. **Which hubs need which playbook?** — K-Means hub segments checked against the Tier 1/2/3 labels (Part D).

A final scoring script combines the Part C classifier with the Part D segments to turn 48 new parcels into an action list. Every number quoted below is copied from a CSV in `outputs/` or `models/`.

## How to run

From a fresh clone, in the repository root:

```bash
pip install -r requirements.txt
python generate_data.py          # prints: 24 1224 48
python part_a_clean_eda.py       # writes data/modelling_table.csv and outputs/part_a_*.csv
python part_b_regression.py      # outputs/part_b_*.csv
python part_c_classification.py  # outputs/part_c_*.csv
python part_d_segments.py        # outputs/hub_profile.csv, part_d_separation.csv, hub_segments.csv, segment_profile.csv, tier_vs_segment_mismatch.csv
python package_model.py          # models/*, outputs/part_d_reload_check.csv
python predict_delay.py          # outputs/new_shipment_actions.csv
```

The scripts must run in this order: each Part reads files written by the one before it.

**About the model file.** `models/delay_model.pkl` is regenerated by running `python package_model.py`. The committed pickle loads reliably only on the scikit-learn version pinned in `requirements.txt` (scikit-learn 1.9.1); when the installed versions differ, re-run `package_model.py` to rebuild it instead of loading the committed pickle. `predict_delay.py` is deterministic — two consecutive runs produce byte-identical `outputs/new_shipment_actions.csv`.

Pinned versions: pandas 3.0.5, numpy 2.5.3, scikit-learn 1.9.1, joblib 1.6.0.

## Data findings

Source files: `outputs/part_a_checks.csv`, `outputs/part_a_delay_by_group.csv`, `outputs/part_a_correlations.csv`.

The raw export had 1,224 rows; 24 exact duplicates were removed, leaving 1,200 shipments. After removing duplicates there were 36 missing distances, 24 missing weights plus 5 scanner-fault sentinel weights (999 kg), 12 missing declared values, 18 missing payment modes and 12 different spellings of `service_type` (3 after cleaning). Gaps were filled with medians from the historical table (distance 314.95 km, weight 1.83 kg, declared value INR 1,121.50). Overall, 278 of 1,200 parcels (delay rate 0.2317) missed their promise.

1. **Service type.** Express is delayed most often: 119 of 243 Express parcels, a delay rate of **0.4897**, against 0.2056 for Standard and 0.0857 for Economy. Express has the tightest promise (36 hours) and also takes the sale-week penalty hardest.
2. **Hub tier.** Delay rate rises steeply with tier: **0.0400** at Tier 1, **0.2150** at Tier 2 and **0.4400** at Tier 3 — Tier 3 hubs miss promises eleven times as often as Tier 1 hubs.
3. **Distance.** Delay rate climbs with every band: **0.0219** (0–200 km), **0.1368** (201–400), **0.4364** (401–600) and **0.8523** (601+ km). Beyond 600 km more than eight in ten parcels are late.
4. **Correlations with `delivery_hours`** (ranked by absolute value, excluding the target itself): `promised_hours` **0.8372**, `distance_km` **0.4013**, `n_stops` **0.3247**. The promise level mostly reflects the service type (Economy parcels have a longer base time), so it dominates; distance and route stops are the main operational drivers.
5. **Why declared value was log-transformed.** On the median-filled column the mean declared value is INR 1,533.05 while the median is INR 1,121.50 — the mean is 37% higher, a sign of a long right tail. After the natural log the mean (7.0277) and median (7.0224) are almost equal, so `log_declared_value` is roughly symmetric and no longer dominated by a few expensive parcels.

The IQR rule (Q1 43.26, Q3 72.56 hours, bounds −0.71 to 116.52) finds only 1 outlier in `delivery_hours`, so no rows were removed.

## Model results (regression)

Source files: `outputs/part_b_*.csv`. Split: 840 train / 180 validation / 180 test. The scaler was fitted on training rows only: the largest absolute column mean of the scaled training rows is 0.0 (machine precision), while for the scaled test rows it is 0.2187 — proof the test rows were not used to fit it.

| model (validation) | MAE | RMSE | R² |
|---|---|---|---|
| mean_baseline | 15.7952 | 18.8552 | −0.0212 |
| linear_regression | 3.9222 | **4.8912** | **0.9313** |
| decision_tree (depth 6) | 5.0971 | 6.2796 | 0.8867 |
| random_forest | 4.2505 | 5.4680 | 0.9141 |
| gradient_boosting | 3.9166 | 4.9165 | 0.9306 |

- **Baseline.** Predicting the training mean for every parcel gives R² = **−0.0212**: it explains none of the variation (slightly worse than the validation mean itself), so any useful model has to beat an RMSE of 18.86 hours.
- **Winner on validation.** Linear regression, RMSE **4.8912 hours** (R² 0.9313), just ahead of gradient boosting (4.9165). The data is mostly additive, which suits a linear model. On the test rows, scored once, it reaches RMSE 4.5235 hours and R² **0.9493**.
- **Bias versus variance (tree depth).** Shallow trees are high-bias: at depth 1 train RMSE is 11.6334 and validation RMSE 12.1324 — both high, with a gap of only 0.50 (12.1324 − 11.6334). Depths 1–3 underfit. Deep trees are high-variance: with no depth limit train RMSE is 0.0000 but validation RMSE is 7.7890 (gap 7.79), and depth 12 shows the same pattern (1.3613 vs 7.4173). The best depth is **6** (validation RMSE 6.2796), 5.85 hours (12.1324 − 6.2796) better than depth 1. All figures from `outputs/part_b_tree_depth.csv`.
- **Learning rate.** 0.1 is best (validation R² 0.9306). At 0.01 the model is too slow: 100 small steps only reach R² 0.7127 — it is still underfitting when it runs out of trees. At 1.0 each tree corrects the previous error in full and overshoots, so R² falls back to 0.8440.
- **Cross-validation versus validation.** With 5-fold CV on the 1,020 train+validation rows (one shared `KFold`), gradient boosting scores mean R² **0.9352** (std 0.0044) against linear regression's **0.9261** (std 0.0048) — the reverse of the validation ranking. The brief's rule makes linear regression the final model scored on test. **If I were shipping, I would choose gradient boosting**: CV averages five 204-row folds instead of one 180-row split, the CV gap (0.009 R²) is about twice the fold-to-fold standard deviation, whereas the validation gap was only 0.025 hours of RMSE, and boosting can also capture the interactions in the data (sale × Express, rain × long distance) that a linear model cannot. Linear regression remains a strong, interpretable fallback.

## Model results (classification)

Source files: `outputs/part_c_*.csv`. Stratified split: 840 / 180 / 180 with 195 / 42 / 41 delayed parcels.

| model (validation, threshold 0.5) | TN | FP | FN | TP | accuracy | precision | recall | F1 |
|---|---|---|---|---|---|---|---|---|
| blind_all_on_time | 138 | 0 | 42 | 0 | 0.7667 | 0.0000 | 0.0000 | 0.0000 |
| logistic_regression | 128 | 10 | 7 | 35 | 0.9056 | 0.7778 | 0.8333 | 0.8046 |
| decision_tree_depth_6 | 128 | 10 | 11 | 31 | 0.8833 | 0.7561 | 0.7381 | 0.7470 |
| random_forest_default | 132 | 6 | 11 | 31 | 0.9056 | 0.8378 | 0.7381 | 0.7848 |

- **Blind baseline.** Calling every parcel "on time" is 0.7667 accurate, yet it catches 0 of the 42 delayed parcels (recall 0). It is useless for operations, whose whole job is to find the late parcels — this is why accuracy alone is not used to judge the models.
- **Noise columns.** The five bookkeeping columns together take **0.2244** of the 17-column forest's importance — a random forest happily splits on random numbers. The F-test is not fooled: all five fall outside the top 7 (ranks 8, 12, 14, 16, 17), with F-scores of at most 4.5847, while the weakest top-7 column (`sale_event_flag`) scores 36.7281. The top seven are `distance_km`, `hub_tier`, `hub_daily_capacity`, `n_stops`, `promised_hours`, `rain_flag`, `sale_event_flag`.
- **The k table.** Validation F1 is 0.6988 at k=5, peaks at **0.8333 at k=7**, then drops to 0.7857 (k=10), 0.8049 (k=12) and 0.7848 (k=17). Five columns are too few (rain and sale effects are lost); adding weak and noise columns beyond seven only lets the forest overfit.
- **Tuning.** On the 7 selected columns, the grid search (27 candidates, 135 fits, best CV accuracy 0.8952, `max_depth=6, min_samples_leaf=1, n_estimators=100`) and the randomized search (9 candidates, 45 fits, best CV accuracy 0.8905) reached validation F1 of 0.7750 and 0.7848 — both **below** the untuned forest's 0.8333. So the final model is the untuned forest (`chosen_from = default_forest_same_7_features`). This says less about tuning than about the validation set: with only 42 delayed parcels, one parcel more or less caught moves F1 by about 0.02, so differences of this size are within noise. The searches also optimised accuracy in CV, not F1.
- **Alert threshold.** Operations rule: the highest threshold whose validation recall is at least 0.80. At **0.5** recall is 0.8333 (35 of 42 caught) with precision 0.7955; at 0.6 recall drops to 0.7619, which breaks the rule even though precision rises to 0.8889. Lower thresholds catch more (0.3 → recall 0.9286) but at the cost of many more unnecessary calls (precision 0.6964). The chosen threshold is **0.5**.
- **Test result (one evaluation).** At threshold 0.5 on the 180 test rows: precision **0.6889**, recall **0.7561**, F1 **0.7209** (31 of 41 delayed parcels caught, 14 unnecessary calls). Test recall is lower than validation recall (0.7561 vs 0.8333) and falls below the 0.80 target. Honestly, the threshold was tuned on validation, so some optimism was expected; and with only 41 delayed test parcels, each missed parcel costs 0.024 recall, so the gap amounts to about three parcels. It is a warning that 0.80 recall is not guaranteed in production; the monitoring plan below watches for it.

## Operations recommendation

For the regional operations head. Source files: `outputs/hub_segments.csv`, `outputs/segment_profile.csv`, `outputs/tier_vs_segment_mismatch.csv`, `outputs/part_d_separation.csv`, `outputs/part_c_final_test.csv`, `outputs/new_shipment_actions.csv`.

**Three hub segments** (K-Means on mean hours, delay rate, mean distance and mean stops per hub):

| segment | hubs | mean hours | delay rate | mean distance (km) | mean stops |
|---|---|---|---|---|---|
| Standard | 7 | 47.24 | 0.0257 | 188.93 | 55.37 |
| Watch | 8 | 56.81 | 0.1550 | 314.18 | 70.72 |
| Escalate | 9 | 64.65 | 0.4600 | 470.48 | 84.34 |

**Escalate hubs** (delay rate): Guwahati HUB19 (0.62), Agartala HUB24 (0.54), Raipur HUB20 (0.48), Nagpur HUB13 (0.46), Patna HUB17 (0.46), Siliguri HUB23 (0.44), Bhubaneswar HUB21 (0.40), Ranchi HUB18 (0.38), Kochi HUB15 (0.36). These hubs need hub-manager escalation for flagged parcels and a review of lane distances and route loads.

**Hubs whose tier label is misleading:**

- **HUB07 Kolkata** — labelled Tier 1 but behaves like a Watch hub (delay rate 0.14, versus 0.00–0.04 for the other Tier 1 hubs).
- **HUB13 Nagpur** — labelled Tier 2 but behaves like an Escalate hub (delay rate 0.46).
- **HUB15 Kochi** — labelled Tier 2 but behaves like an Escalate hub (delay rate 0.36).
- **HUB22 Dehradun** — labelled Tier 3 but behaves like a Watch hub (delay rate 0.20).

The tier label should not be used to decide a hub's playbook: use the segment, which reflects how the hub actually performs. The label is also a model input (`hub_tier`), so for these four hubs the classifier is fed a misleading signal — another reason to review the labels.

**Alerts.** The alert threshold is **0.5**. On the test set, about **7 of every 10 flagged parcels are really delayed** (precision 0.6889) and about **7 to 8 of every 10 delayed parcels are caught** (recall 0.7561).

**New parcels.** Of the 48 parcels about to be dispatched, **8 are flagged**: **6 need escalation to the hub manager** (Escalate-segment hubs HUB24, HUB18, HUB17, HUB20 and two at HUB21) and 2 need a proactive customer call (HUB22 and HUB09, both Watch). The remaining 40 need no action.

**Why K = 3.** The across-to-within distance ratio rises with K — 2.894 (K=2, sizes 15-9), 5.3928 (K=3, 9-8-7), 6.3047 (K=4, 8-7-5-4), 6.8866 (K=5, 8-7-4-3-2) — because more clusters always make each cluster tighter. But K = 4 contains clusters of 5 and 4 hubs and K = 5 of 4, 3 and 2 hubs; a segment of fewer than 6 hubs is too small to carry its own playbook. K = 3 gives balanced segments of 9, 8 and 7 hubs, nearly doubles the separation of K = 2, and matches the three playbooks operations actually runs.

## Production plan

**(a) Production-readiness characteristics mapped to the repository**

| characteristic | where it lives |
|---|---|
| Accuracy | `outputs/part_c_final_test.csv` — one untouched test evaluation (F1 0.7209); `outputs/part_b_metrics.csv` test row (R² 0.9493) |
| Reliability | `outputs/part_d_reload_check.csv` — the reloaded pickle reproduces the in-memory probabilities exactly (max difference 0.0); `predict_delay.py` asserts no missing model inputs |
| Reproducibility | `requirements.txt` pins exact versions; every `random_state` is fixed; `generate_data.py` is committed verbatim; `predict_delay.py` gives byte-identical output on repeat runs |
| Performance (speed) | `predict_delay.py` scores the 48-parcel batch in under a second including Python start-up with a 100-tree forest on 7 selected columns — fast enough to run at every dispatch wave |
| Maintainability | one shared module `src/shipment_prep.py` holds the constants and the two preprocessing functions; each Part is a separate script with one job |
| Consistency (same preprocessing) | `predict_delay.py` calls the same `clean_shipments` and `build_features` as training, with the stored medians from `models/impute_values.csv` and the column order from `models/feature_order.csv` |
| Monitorability | `outputs/new_shipment_actions.csv` logs every probability, flag and action per parcel, so flag rate and later outcomes can be tracked |

**(b) What to monitor, with triggers**

| quantity | normal level (from this project) | trigger for review |
|---|---|---|
| Weekly delayed share of delivered parcels | 0.2317 | outside 0.18–0.29 for two consecutive ordinary weeks |
| Weekly share of parcels flagged | 8 of 48 new parcels (≈ 0.17); test set 45 of 180 (0.25) | below 0.12 or above 0.35 |
| Recall on parcels whose outcome is now known | 0.7561 on test, target ≥ 0.80 | below 0.70 over a rolling four weeks (≥ 40 delayed parcels) |
| Precision of flags (calls that were needed) | 0.6889 on test | below 0.55 over four weeks |
| Input drift: mean `distance_km`, share of missing values filled with a median | mean distance 314.95 km (median); 36 of 1,200 distances missing | mean distance moves by more than 15%, or more than 5% of any field needs filling |

**(c) Retraining and the sale window**

- **Schedule:** retrain monthly on a rolling window of the latest delivered parcels, and immediately when a recall or drift trigger fires. Re-run the whole pipeline (Parts A–D) so the medians, scaler, selector, threshold and hub segments are all refreshed together, and re-check the threshold rule on the new validation split before deploying.
- **Sale window (15–28 September, `sale_event_flag`):** sale weeks add hours to every parcel and much more to Express parcels, so delay and flag rates will jump. Compare sale weeks against the previous sale event, not against ordinary weeks — otherwise every sale would fire a false drift alarm, and the trigger bands above apply only to ordinary weeks. Make sure each training window contains at least one sale period so the model has seen it.
- **What drift would look like here:** a hub opening new long lanes (mean distance rising), routes getting heavier (`n_stops` rising), a monsoon season with a much higher `rain_flag` share than the 18% in the history, a shift in service mix toward Express, or a hub's behaviour changing segment (as Kolkata, Nagpur, Kochi and Dehradun already differ from their labels). The signs are flag share and delay share moving apart, or recall on known outcomes falling.

## Limitations

1. **Synthetic data.** Every row comes from `generate_data.py`, whose delay process is additive with simple interactions and Gaussian noise. Real Delhivery parcels have messier causes (address quality, rider absence, failed first attempts) that this pipeline never saw, so the accuracy figures will not transfer directly.
2. **Small test set.** The test set has only 41 delayed parcels, so one parcel moves recall by about 0.024. The test recall of 0.7561 has a wide uncertainty and could easily be several points higher or lower on another sample.
3. **Threshold tuned on one validation split.** The 0.5 threshold and the choice of the untuned forest come from a single 180-row validation set with 42 delayed parcels. Test recall already fell below the 0.80 target; a cross-validated or larger-sample threshold choice would be more robust.
4. **Hub segments rest on 24 hubs with 50 parcels each.** Hub delay rates move in steps of 0.02, so a hub near a segment boundary (for example Kochi at 0.36 or Coimbatore HUB14 at 0.24) could change segment with a few more parcels.
5. **Tier label as a feature.** `hub_tier` is a model input, yet four hubs' labels do not match their behaviour; the classifier inherits that error for those hubs.
6. **No time-based validation.** The splits are random rather than by dispatch date, so the evaluation does not show how the model ages; the 90-day history also contains only one sale event.
